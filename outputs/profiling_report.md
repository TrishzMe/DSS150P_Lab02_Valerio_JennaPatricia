## 2. Schema Findings

**customers.csv** — 7 columns, all delivered as text (CSV is untyped):
`customer_id` (string, key), `first_name`, `last_name`, `email`, `city` (strings),
`signup_date` (date delivered as `YYYY-MM-DD` text), `customer_segment` (controlled
vocabulary: Professional, Retail, SME, Student).

**orders.json** — root is a list of 250 objects. Top-level keys: `order_id`, `customer_id`,
`order_timestamp` (ISO-8601 string, logically a timestamp), `status`, `item_count` (int),
`subtotal` / `total_amount` (float), `shipping_fee` (numeric; observed as int), and the
nested object `shipping{region, method}`. No nulls or missing keys observed.
The nested object could be (a) flattened into `shipping_region`/`shipping_method`
columns, (b) kept as a JSON/VARIANT column, or (c) normalized into a child table.

**products.parquet** — 200 x 7 with an embedded, typed schema:
`product_id`, `product_name`, `category`, `brand` (string), `unit_price` (float64),
`stock_quantity` (int32), `weight_kg` (float64). Types survive a round trip without
re-inference; a CSV re-read of the same data changed `stock_quantity` to int64.
Size comparison: parquet 14,652 B vs CSV 11,560 B vs JSON 40,686 B — on 200 rows the
columnar/dictionary overhead makes Parquet *larger* than CSV; its compression and typing
advantages appear at scale, which is one reason it is a storage/analytics format rather
than a common operational hand-off format (operational systems emit rows one at a time;
Parquet files are immutable columnar batches that are awkward to append to).

**REST API `/api/events`** — pagination envelope `page`, `per_page`, `total`, `has_more`,
`next_page`, `items`. Each item: `event_id`, `customer_id`, `event_type`, `amount` (float),
`updated_at` (ISO-8601 string), nested `metadata{channel, campaign}`. Supports
`updated_after` for incremental pulls. At per_page=10 the data spans 13 pages, so reading
only page 1 would silently drop over 90% of the records — pagination must be followed
until `has_more` is false.

**PostgreSQL `support_tickets`** — typed relational schema with declared constraints:
`ticket_id` INTEGER PRIMARY KEY, `customer_id`/`category`/`priority`/`status` VARCHAR NOT
NULL, `assigned_agent` VARCHAR NULL, `opened_at` TIMESTAMP NOT NULL, `resolved_at`
TIMESTAMP NULL. Unlike the files, nullability and the key are enforced by the engine.

## 3. Data Quality Findings (documented observations)

1. **customers.csv — key collision:** `C0090` appears on two rows describing *different
   people* (Paolo Aquino / Marikina vs Hannah Reyes / Caloocan). This is not a re-delivered
   row; it breaks the uniqueness assumption for the candidate key.
2. **customers.csv — exact duplicate rows:** `C0036` and `C0145` each appear twice with
   all seven fields identical (likely re-delivery/append artifacts).
3. **customers.csv — missing values:** 3 rows lack `email`, 2 rows lack `city`.
4. **API — intentional duplicate event_ids:** `E0020` and `E0055` are each delivered twice
   with different `updated_at` values; the newer record supersedes the older, so
   deduplication must keep max(`updated_at`) per `event_id`, not an arbitrary row.
5. **support_tickets — nullable operational fields:** 4 tickets have no `assigned_agent`;
   125 have NULL `resolved_at`. The latter is legitimate (unresolved tickets), so NULL here
   is state, not an error — a contract should distinguish the two cases.
6. **orders.json / API — type erosion:** timestamps arrive as JSON strings and must be
   declared logically as timestamps; `shipping_fee` arrives as int on observed rows but is
   logically a decimal amount.

## 4. Recommended Acquisition Method

| Source | Method | Rationale |
|---|---|---|
| customers.csv, orders.json, products.parquet | Full file copy into `raw/files/` with SHA-256 manifest | Small full-snapshot files; hash prevents duplicate ingestion on rerun |
| REST API events | Paginated GET with `updated_after` watermark into `raw/api/events.jsonl` | Source supports incremental filtering; watermark avoids re-pulling history |
| PostgreSQL support_tickets | Inspection only this lab; future: incremental by timestamp column or CDC | Bounded queries protect the operational source |

## 5. Risks and Assumptions

- Assumes `updated_at`/`order_timestamp` are in a single consistent timezone; strings carry
  no offset, so ingestion records its own UTC `_ingested_at` for lineage.
- The strict watermark (`updated_after >` last value) can drop records that share the
  boundary timestamp if the source later delivers more rows at exactly that time.
- CSV key collisions (C0090) mean downstream must not blindly primary-key on
  `customer_id`; the raw area preserves both rows and defers resolution.
- Profiling used full reads of small local files; against production sources the same
  questions must be answered with bounded/sampled queries to avoid degrading the source.
